## 1. B7 · 含税/未税契约分叉（Budget · project_versions 列）

| 项 | 内容 |
|---|---|
| **现状** | 规则文档口径：「明细列未税、展示 ×(1+税)」；代码实际**存含税**、展示不乘（前端自洽，后端消费方不二次计税） |
| **影响** | 契约文档与实现长期分叉；无功能错误，但新接手者按文档理解会双重计税 |
| **改动风险** | 改动任一侧（存改未税，或展示改乘）都有**双重计税风险**——消费方可能已按现有约定二次计税 |
| **建议动作** | **文档对齐实现（零代码风险）**：将契约明确为「列持久化含税、明细展示未税换算、汇总含税」，写入家族清单/规范。代码不动 |

## 2. B3 · 报价草稿客户名/销售编号可编辑（Budget · ProjectHeader）

| 项 | 内容 |
|---|---|
| **现状** | 报价草稿态可编辑 `clientName`/`salesNo`；机会侧同名字段创建后只读 |
| **影响** | 两页同名字段口径分裂（机会锁定 vs 报价草稿可改）；无数据错误 |
| **改动风险** | 若锁定报价草稿字段，会阻断合法修正（如录错客户名后无法改） |
| **建议动作** | **维持现状**：机会与报价是独立记录，机会锁定源于「创建后不可改归属」，报价草稿允许修正是产品自由选择 |

## 3. D1 · 历史周编辑权限（TR · TimeRecord）

| 项 | 内容 |
|---|---|
| **现状** | 唯一门禁是 `weekFrozen`（已提交周冻结）；历史未提交周可自由编辑/增删（补录） |
| **影响** | 规则文档写「当前周开放；历史周只读」，但产品允许补录是有意设计 |
| **改动风险** | 锁定历史周会**阻断补录**（如漏记一周后无法回填） |
| **建议动作** | **确认补录是否允许**：允许 → 维持现状；不允许 → 需先定「已提交/跨周是否冻结」规则再改 |

## 4. D2 · 补班日请休假（TR · TimeRecord）

| 项 | 内容 |
|---|---|
| **现状** | `MAKEUP_WORKDAYS`（周六补班）计入应出勤分母，但 `validateGrid` 对周末一律拒请休假 → **补班日请假被拦、开工率分母不减** |
| **影响** | 补班日请假无法提交（后端 `assertLeaveValid` 同样按周末拒，注释明确「MAKEUP_WORKDAYS 仅前端使用」） |
| **改动风险** | 支持补班日请休假需**前后端同改 + HR 规则确认**（补班日的请假口径、调休规则） |
| **建议动作** | **暂缓**：需 HR 先确认「补班日是否允许请假、如何计考勤」，确认后再定方案 |

## 5. D3 · 全天请休假上限口径（TR · TimeRecord）

| 项 | 内容 |
|---|---|
| **现状** | `TimeRecord.jsx` L133/L141：请休假单日合计 **≤ 8 小时**；而时段系统上午(4.5)+下午(4.5)=**9 小时** |
| **影响** | **全天请假必被拦**（须手动把上/下午拆短压到 ≤8h）——高频误拦场景 |
| **改动风险** | 直接放宽到 9h 会改变考勤口径，需确认规则「单日工时上限」到底按 8h 还是 9h 计 |
| **建议动作** | **产品确认上限口径**：若全天可请 → 上限改为时段日净工时 9h（或全选时豁免）；若仍 8h → 保持现状并给「全天请假」一键拆段提示 |

## 决策方式

每项只需在标题行前加状态标记后回填即可：
- `[已定] 采纳建议动作` —— 按「建议动作」执行（B3/B7 可直接采纳）
- `[已定] 其他口径` —— 写明决定，另行排期实现
