# 08 蓝表赢率详解

> **本章学习目标**
> 1. 理解"蓝表"背后的策略销售方法论（EB/UB/TB/COACH 角色模型）；
> 2. 逐段读懂 `calcBlueTableWinRate` 的赢率计算公式；
> 3. 学会把"一个方法论"翻译成"一段可测试的纯函数"。

## 8.1 蓝表是什么：策略销售方法论

销售跟单到"机会"阶段，最大的问题是：**这家客户到底会不会买？关键人是谁？支持我们还是反对我们？** 拍脑袋判断赢率往往失真。蓝表（Blue Table）是一套结构化的评估工具，出自策略销售（Strategic Selling）方法论：

1. **识别决策角色**——一张订单背后有四种角色：
   | 角色 | 含义 | 影响力特点 |
   |---|---|---|
   | **EB**（Economic Buyer） | 经济买家：掏钱的人/决策拍板人 | 影响力最大 |
   | **UB**（Technical Buyer） | 技术买家：做技术评估、把关的人 | 影响技术方向 |
   | **TB**（User Buyer） | 用户：真正使用产品的人 | 影响使用评价 |
   | **COACH**（教练） | 内部向导：给你提供信息、帮你说话的人 | 信息与推动力 |

2. **评估每个角色的支持度**（support，-5 反对 ~ +5 支持）、影响力权重、是否缺失。
3. **结合报价竞争力**（pricing）、预算情况（veto_budget）、时间节点（timeline_option）、客户定位（positioning）、反应模式（reaction_mode）综合打分。

结果就是 0~90 的赢率（封顶 90，永远不写 100——给自己留余地，也防止过度自信）。这个赢率同步到机会表的 `win_rate`，用于销售漏斗排序。

## 8.2 数据结构

```ts
// BlueTable
{
  vetoBudget: 'ok' | 'possible' | 'failed',    // 预算：正常 / 紧张 / 否决
  budgetAmount?: number,
  timelineOption: 'optimistic' | 'neutral' | 'negative',  // 时间线
  pricing: PricingLevel,                        // 价格竞争力 7 档
  positioning: number,                          // 客户定位 1~10（陶醉→惊慌）
  reactionMode: 'G' | 'T' | 'EK' | 'OC',       // 反应模式
  targets: [...],                               // 行动目标
  roles: BlueTableRole[],
}

// BlueTableRole
{ roleType: 'EB'|'UB'|'TB'|'COACH', name, influence: 'high'|'medium'|'low', influenceWeight: number, support: number /* -5~5 */, demandFit, relationship }
```

## 8.3 常量表（公式的参数）

```ts
/** 价格竞争力对应的百分点修正值 */
export const PRICING_ADJUSTMENTS: Record<PricingLevel, number> = {
  very_strong: 15, strong: 10, competitive: 5, neutral: 0,
  slightly_weak: -5, weak: -10, very_weak: -15,
};

/** 影响力默认权重 */
const INFLUENCE_DEFAULT_WEIGHT = { high: 5, medium: 3, low: 1 };
/** EB 角色专用权重（决策者影响力更大） */
const EB_INFLUENCE_WEIGHT = { high: 10, medium: 5, low: 1 };
```

**EB 权重翻倍**：因为经济买家的支持与否对整个成交影响最大，所以 high 给 10 而不是 5。

## 8.4 逐段读 `calcBlueTableWinRate`

函数返回 `CalcIntermediate`——不仅是最终赢率，还包含**所有中间值**，这样 UI 能展示"扣分扣在哪了"（诊断价值）。

```ts
export function calcBlueTableWinRate(blueTable: BlueTable): CalcIntermediate {
  const result: CalcIntermediate = { vetoed: false, baseSupportScore: 0, rolePenalty: 1, ... };

  // ── 1 否决检查：预算失败或时间线负面 → 直接 0 ──
  if (blueTable.vetoBudget === 'failed' || blueTable.timelineOption === 'negative') {
    result.vetoed = true;
    result.finalRate = 0;
    return result;
  }

  const roles = blueTable.roles;
  if (roles.length === 0) { result.finalRate = 0; return result; }   // 没填角色 → 0
```

**否决逻辑**：`vetoBudget=failed`（客户明确说没钱）或 `timelineOption=negative`（时间线非常不利）是**一票否决**，直接判 0。这体现了"策略销售"的第一原则：**先看这单值不值得打**，不值得就直接 0，省得浪费资源。

```ts
  // ── 2 角色缺失判断（是否有至少一人担任该角色类型） ──
  const hasEB = roles.some(r => r.roleType === 'EB');
  const hasCoach = roles.some(r => r.roleType === 'COACH');
  result.missingEB = !hasEB;
  result.missingCoach = !hasCoach;

  if (!hasEB && !hasCoach) result.rolePenalty = 0.4;   // 两个关键角色都没有 → 打 4 折
  else if (!hasEB)           result.rolePenalty = 0.5; // 缺 EB → 打 5 折
  else if (!hasCoach)        result.rolePenalty = 0.85;// 缺 COACH → 打 8.5 折
  else                       result.rolePenalty = 1.0;
```

**角色缺失惩罚**：EB 是拍板人，没找到 EB 意味着"不知道谁说了算"，赢率要大打折扣；COACH 是内部向导，没找到意味着"信息不透明"。两者都缺 = 最坏情况（0.4）。

```ts
  // ── 3 支持度加权平均（influenceWeight 直接作为权重） ──
  let totalWeight = 0, weightedSupport = 0;
  for (const role of roles) {
    const w = Number(role.influenceWeight ?? 0);          // ⚠️ Number(??0) 防御畸形数据
    const normSupport = (Number(role.support ?? 0) + 5) / 10;   // -5→0, 0→0.5, +5→1
    totalWeight += w;
    weightedSupport += w * normSupport;
  }
  if (!(totalWeight > 0)) { result.finalRate = 0; return result; }  // 权重和无效 → 0

  result.baseSupportScore = (weightedSupport / totalWeight) * 100;
```

**支持度加权**：
- 每个角色的支持度 `support`（-5~+5）归一化成 0~1（`(s+5)/10`）；
- 用 `influenceWeight` 作为权重求**加权平均** → `baseSupportScore`（0~100）。
- ⚠️ `Number(role.influenceWeight ?? 0)`：`Number()` 包裹 + `?? 0` 兜底，是为了防御数据库里存了 `"3"`（字符串）或 `NaN` 的脏数据，不让它污染加权和。

```ts
  // ── 4 反应模式修正 ──
  result.reactionFactor = blueTable.reactionMode === 'OC' ? 0.8 : 1.0;

  // ── 5 乘法链：支持度 × 角色系数 × 反应系数 ──
  result.midRate = result.baseSupportScore * result.rolePenalty * result.reactionFactor;

  // ── 6 价格竞争力修正（加法） ──
  result.pricingAdjustment = PRICING_ADJUSTMENTS[blueTable.pricing] ?? 0;
  const withPricing = result.midRate + result.pricingAdjustment;

  // ── 7/8 预算与时间线扣减（中性时小幅扣分） ──
  result.budgetPenalty = blueTable.vetoBudget === 'possible' ? 5 : 0;
  result.timelinePenalty = blueTable.timelineOption === 'neutral' ? 5 : 0;
  const withPenalties = withPricing - result.budgetPenalty - result.timelinePenalty;

  // ── 9 封顶 0~90 ──
  result.finalRate = Math.max(0, Math.min(90, Math.round(withPenalties)));
  return result;
}
```

**修正的顺序（乘法先，加法后）**：
- 乘法链：`baseSupportScore × rolePenalty × reactionFactor`——支持度、角色、反应是"结构性"因素，用乘法（互相放大/缩小）；
- 加法修正：`± 价格竞争力`，`− 预算紧张 5`，`− 时间线中性 5`——这些是"边际"因素，用加法；
- **封顶 0~90**：`Math.max(0, Math.min(90, ...))`——不取负、不超 90。

### 为什么 `reactionMode === 'OC'` 只乘 0.8？

OC（自满，认为现状挺好）是最难撬动的客户——"我们很好，不需要你的东西"，所以要大幅折扣。G（增长，想变更好）反而是最容易争取的（不折扣）。

## 8.5 一张图记住整个公式

```
否决？(预算 failed / 时间线 negative)  → 0
  ↓
支持度加权平均 × 角色缺失系数 × 反应模式系数   ← 乘法链（结构性）
  ↓
+ 价格竞争力修正（-15 ~ +15）                  ← 加法（边际）
− 预算紧张 5（possible）
− 时间线中性 5（neutral）
  ↓
clamp(0, 90)
```

## 8.6 测试怎么看（tests/blueTableCalculation.test.ts）

赢率函数是**纯函数**，测试直接构造 BlueTable 对象断言：

```ts
// 示例（示意，具体以实际测试为准）
it('否决 → 0', () => {
  const r = calcBlueTableWinRate({ vetoBudget: 'failed', roles: [{ roleType: 'EB', influenceWeight: 5, support: 5 }] });
  expect(r.vetoed).toBe(true);
  expect(r.finalRate).toBe(0);
});
```

测试覆盖的边界包括：空角色、畸形权重、否决、封顶、各修正档位——把"方法论"的每个分支都锁死。

## 8.7 蓝表数据的存取（前端 → 后端）

- 前端 `BlueTableModal.tsx` 编辑蓝表（角色网格 + 实时赢率预览）；
- 保存：`opportunityService.saveBlueTable(id, { ...蓝表, roles })` → `PUT /opportunities/:id/blue-table`；
- 后端 `opportunities.ts`：`withTransaction` 内 upsert 蓝表 + **整组替换角色**（先 DELETE 全部再 INSERT，同一事务）；
- 赢率写入：保存时前端算好 `win_rate` 同步到机会（或由列表 JOIN 蓝表动态展示）；
- 列表：`GET /opportunities` 用 `LEFT JOIN blue_tables` + 子查询 `jsonb_agg` 把角色聚合进 `blue_table.roles`。

## 8.8 本章小结

- 蓝表 = 策略销售方法论的可执行化：先否决、再结构性乘法、再边际加法、最后封顶 0~90。
- `calcBlueTableWinRate` 返回中间值 → 既能算赢率又能做诊断。
- 方法论 → 纯函数 → 测试锁定，这是"把业务知识变成代码资产"的完整范式。

**本章练习**：构造 3 个场景的 BlueTable 对象（全支持高权重 / 缺 EB / 预算紧张+价格很弱），手算期望赢率，写进测试跑通。然后打开蓝表弹窗，改一个角色的支持度，观察赢率实时变化的逻辑是否符合公式。
