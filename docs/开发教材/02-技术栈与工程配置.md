## 2.2 五大设计取向（理解代码的钥匙）

这五条贯穿三个代码库的所有代码。读代码前先内化它们。

### 取向 1：纯函数优先、可测优先

业务计算（成本、赢率、工时、财年）都提取成**无副作用、参数进参数出**的纯函数，放在 `utils/`（前端）或 route 文件顶部 `export`（后端）。

```ts
// 前端 utils/calculations.ts
export function calcDirectCost(item): number { ... }

// 后端 routes/timerecording.ts（函数写在文件顶部并导出）
export function serverHours(start?: string | null, end?: string | null): number { ... }
```

**为什么**：
- 纯函数不依赖 DOM、不依赖时间、不依赖全局状态 → 单测可以直接喂数据断言（不用 mock 任何东西）；
- 页面只是"调用方"，同一套口径被多个页面共享 → 不会出现两个页面算出来的数不一样。

**代价**：写代码时要多想一步"这段逻辑是不是该放进 utils"，但它带来的可测性和复用性远超这点成本。

### 取向 2：单一来源（Single Source of Truth）

同一套规则**只允许定义一处**，其余引用。例如：

| 规则 | 定义处 | 谁引用 |
|---|---|---|
| 权限守卫清单 | 后端 `permissions.ts`（WRITE_GUARD/READ_GUARD） | 后端 routes/index.ts + 前端 permissions.ts（镜像） |
| 前端路由所需权限 | 前端 `utils/permissions.ts` | App.tsx 守卫、AppLayout 菜单 |
| 颜色语义色板 | `styles/colors.ts` / `colors.js` | 所有页面 |
| 全局常量 | `utils/constants.ts` / 后端 `constants.ts` | 所有页面/路由 |
| 财年/销售/交付统计口径 | `utils/analysisShared.ts` | Dashboard/SalesAnalysis/DeliveryAnalysis |
| 节点状态文案 | `NODE_STATUS_META` | 多处 |

**为什么**：最可怕的 bug 不是"逻辑错了"，而是"两处口径打架"（同一个指标两个页面算出来不一样）。收敛到一处后，改一处全变，且用单测锁住。

### 取向 3：服务端权威

凡是"业务状态、金额、工时、审批状态、生命周期时间戳"，**最终以服务端计算/校验为准**，前端传值只是建议。

典型例子：
- 工时记录：`hours`/`hour_type`/`year`/`week_number` **前端不传、后端重算**（S4 修复）；
- 报价审批状态：`status` 只能经审批流程流转，请求体直设被剥除（`excludeOnCreate`）；
- 机会生命周期：`won_at`/`lost_at`/阶段时间戳由后端状态机采集，客户端直写被忽略。

**为什么**：前端可以被伪造（DevTools 改请求体）、可以绕过 UI（直接调接口）。业务规则的最终防线必须在后端。

### 取向 4：前后端命名边界清晰（camelCase ↔ snake_case）

- 前端内部：**camelCase**（`clientName`、`totalCost`）；
- 数据库列：**snake_case**（`client_name`、`total_cost`）；
- 转换只发生在两个点：
  - 前端 `api.ts`：POST/PUT 请求体自动 `toSnake()`，GET 响应自动 `toCamel()`；
  - 后端 `helpers.ts`：`objKeysToSnake()` 兜底转换请求体。

**为什么**：后端经常 `SELECT *` 返回整行（键名就是列名）。如果不统一转换层，就会出现"有的接口 camel、有的接口 snake"的混乱，前端类型对不上。统一后，前端永远面对 camelCase 的 TS 类型。

> ⚠️ 注意：**TR 前端不转换**，直接用后端的 snake_case 字段（`cost_center`、`start_time`）。所以 TR 的代码里全是 snake_case，而 Budget 里是 camelCase。这是两套前端的**有意差异**，别在 Budget 里写 snake_case（lint-naming 会拦）。

### 取向 5：注释记录"为什么"

代码里有大量 `// ⚠️ 编号 修复：原因` 注释：

```ts
// B61 修复：已通过/已驳回的报价被再次编辑保存时状态重置为草稿——否则内容已修改却仍保持 approved/rejected，
// 绕过审批状态机（改过数据不经重审即显示"已通过"）。
const statusForSave = reviewStatusForSave(curVer.reviewStatus);
```

**为什么**：代码能说明"怎么做的"，只有注释能说明"**为什么这么做**"。每次修复线上 bug 时把原因写下来，后来者（包括未来的自己）就不会"优化掉"一个看似多余的检查。编号（B61/A105/S4）是历史批次号，用于和测试用例、文档、记忆互相对照。

> 规则细节见 `docs/注释规范.md`。

## 2.3 工程配置逐项解读

### 2.3.1 Budget 的 `package.json` scripts

```json
"scripts": {
  "dev": "vite",
  "build": "node scripts/lint-naming.cjs && npm run lint:quiet && tsc -b && vite build && npx vitest run",
  "lint:quiet": "eslint . --no-ignore --quiet || true",
  "typecheck": "tsc -b",
  "lint": "eslint .",
  "test": "vitest run",
  "coverage": "vitest run --coverage",
  "bench": "vitest run --config vitest.bench.config.ts",
  "preview": "vite preview"
}
```

**`build` 是"门禁链"**，五关全过才算构建成功：

```
node scripts/lint-naming.cjs   # ① 命名规范：蛇形键名 / 裸 fetch 扫描
npm run lint:quiet             # ② ESLint（--quiet 只报 error，|| true 不阻塞？见下方⚠️）
tsc -b                          # ③ 类型检查（必须用 -b，见下方⚠️）
vite build                      # ④ 生产构建
npx vitest run                  # ⑤ 全量单测
```

- ⚠️ `lint:quiet` 末尾的 `|| true`：历史上 lint 还有存量 warning，用 `--quiet` 只留 error；`|| true` 是"即使退出码非 0 也不中断"。这是**过渡期的妥协**——它的存在意味着 lint 里其实没有必须通过的 error 了（项目已清零），但为了稳妥保留。真正必须过的是 `tsc -b` 和 `vitest`。
- ⚠️ **类型检查必须用 `tsc -b`，不能用裸 `tsc --noEmit`**。这个项目用 TypeScript 的 project references（`tsconfig.json` 里只有 `references`，指向 `tsconfig.app.json` 和 `tsconfig.node.json`）。裸 `tsc --noEmit` 会对着一个空文件列表"静默通过"，等于没检查。这是个经典陷阱，详见记忆 `tsc-solution-config-trap`。

### 2.3.2 Vite 配置（Budget）

```ts
// vite.config.ts
export default defineConfig({
  base: '/budget/',          // 部署在 nginx 的 /budget/ 子路径下
  plugins: [react()],
  server: {
    proxy: {
      '/api': {
        target: process.env.VITE_PROXY_TARGET || 'http://118.89.92.58',  // 开发时 /api 代理到后端
        changeOrigin: true,
      },
    },
  },
})
```

要点：
- **`base: '/budget/'`**：产物引用路径都以 `/budget/` 开头，配合 nginx 子路径部署。TR 同理用 `base: '/timerecording/'`。
- **开发代理**：开发时页面访问 `/api/...` 会被 Vite 代理到 `target`。默认指向**生产服务器**（`118.89.92.58`）——也就是说你本地不启动后端也能调线上的 API 数据（对调试 UI 很方便）。想连本地后端，启动时设置 `VITE_PROXY_TARGET=http://localhost:3001`。

### 2.3.3 tsconfig 三件套（Budget）

```
tsconfig.json          # 空壳，只有 references 指向下面两个
tsconfig.app.json      # src/ 的编译配置（DOM 环境、JSX、strict）
tsconfig.node.json     # vite.config.ts 等 node 端文件的配置
```

这就是"project references"：把"应用代码"和"构建工具代码"分成两个编译单元。`tsc -b` 会按依赖顺序分别构建。

### 2.3.4 ESLint 配置

三个库都基于 `@eslint/js` + `typescript-eslint` + `eslint-plugin-react-hooks` + `eslint-plugin-react-refresh`。TR 的 build 里显式加了 `eslint . --quiet`（P0 门禁补漏——此前 TR 只跑 vite+vitest，渲染期 `Date.now()` 等 react-hooks/purity 错误漏网）。

### 2.3.5 vitest 配置（Budget）

```js
// vitest.config.js
export default defineConfig({
  test: {
    environment: 'node',                    // 纯函数测试，不需要 DOM
    include: ['tests/**/*.test.{ts,tsx,js,jsx}'],
    coverage: { provider: 'v8', include: ['src/**'], reporter: ['text', 'html'] },
  },
})
```

要点：**测试放根级 `tests/`**（不在 `src/` 里）。原因：lint-naming 会扫描 `src/` 里的蛇形键名，而测试数据里充满了 snake_case 字段（模拟数据库返回），放 src 会误报。测试用 node 环境即可——被测的都是纯函数，不需要浏览器。

### 2.3.6 后端配置

```json
// backend/package.json scripts
"dev":   "tsx watch src/index.ts",   // tsx 直接跑 TS，watch 热重载
"build": "tsc && vitest run",        // 门禁：类型检查 + 单测
"start": "node dist/index.js",       // 生产运行编译产物
```

- **开发**：`tsx watch`（不编译，直接执行 TS）；**生产**：先 `tsc` 编译到 `dist/` 再 `node dist/index.js`。但部署脚本实际是直接发 `src/` 上去用 tsx 跑（见 16 章）。
- **vitest 配置**（`backend/vitest.config.ts`）有一段很巧妙：

```ts
env: {
  DB_PASSWORD: 'test-no-connect',     // 让 pool.ts 能加载（它要求 DB_PASSWORD 必填）
  DB_PORT: '5432',
  JWT_SECRET: 'vitest-only-secret-0123456789abcdef0123456789',  // 让 auth.ts 能加载（要求 ≥32 位）
},
```

后端测试只测纯函数，**不会真的连数据库**（pg.Pool 是惰性建连）。但 `pool.ts` 和 `auth.ts` 在**模块加载时**就检查环境变量（不存在就 `process.exit`），所以测试环境要提供假值让模块能加载。这是"测试环境如何伺候启动期副作用"的一个典型解法。

## 2.4 本章小结

- 技术栈 = React + antd + Vite（前端）× 2，Express + PostgreSQL（后端）× 1。
- 五大设计取向（纯函数、单一来源、服务端权威、命名边界、注释为什么）是读代码的总纲。
- `npm run build` 是门禁链：命名 → lint → 类型（tsc -b）→ 构建 → 测试，五关全过才算通过。

**本章练习**：打开 `backend/package.json`、`BudgetEstimateApp/package.json`、TR `frontend/package.json`，对照本文逐条说出每个 script 在做什么；再打开三个 vite 配置，说出 `base` 和 `proxy` 的作用。
