# 10 交付与销售分析

## 10.1 转交付：从"销售"到"执行"

报价审批通过、客户签单后，机会要转成交付项目。这是两个域的分界线：

```
销售域：sales_opportunities（机会） + quotations（报价，status=approved）
   │  转交付（POST /deliveries）
   ▼
交付域：delivery_projects（交付项目）+ delivery_nodes（15 个节点）
```

**转交付的触发点**（`DeliveryManagement.tsx` + 后端 `deliveries.ts beforeCreate`）：
- 机会必须真实存在、报价必须真实存在且归属一致；
- 同一机会**只能转一次**（`uq_delivery_opportunity` 唯一约束）；
- 转交付时机会**置为"赢/中标"并记 `won_at`**（这是"赢单"的终极确认）——即使之前标过"输"，转交付也视作赢单（因为合同真的签了）。

**编号模型**：
- 机会/客户报价：`A{YYYY}-{MM}-{NNN}-S`；
- 交付：转交付时由销售编号派生（后缀变 `-E`）；
- 机会与交付**共用同一个 `-S` 报价**，交付取它的概算成本作为执行基线。

## 10.2 交付节点与延期判定

### 10.2.1 15 个标准节点

`NODE_NAMES`（前端 `utils/constants.ts`）定义了 15 个标准节点：项目启动、详细设计、采购、装配调试……直到**节点 15 项目总结**。节点 15 的实际完成日 = **项目交付完成日**（财年归集的锚点）。

### 10.2.2 状态三态化

```
节点：pending（未开始） → in_progress（进行中） → completed（已完成）
项目：未开始 → 进行中 → 已完成
```

"延期中"是一个**派生维度**，不是存储状态——由"当前时间 vs 基线"计算得出。

### 10.2.3 延期判定（共享函数，全页面同口径）

```ts
// utils/analysisShared.ts（示意，具体签名以实际为准）
function getNodeDelay(node, now) {
  if (!node.baselinePlannedEndDate) return undefined;   // 无基线不判定
  if (node.status === 'completed')
    return actualDate 与 基线 比较;                       // 已完成：实际完成日 vs 基线
  return now 与 基线 比较;                                 // 未完成：判定时点 vs 基线
}
```

**两条铁律**：
1. **无基线不判定**（`baselinePlannedEndDate` 缺失 → 返回 undefined，不判"按时"也不判"延期"）。这是 A2 修复——之前 Dashboard 把无基线节点计为"按时"，恒 100%，与交付分析打架。
2. **已完成按实际完成日、未完成按当前判定时点**。更新计划排后（重新计划）**不计延期**——延期是"超出最初审批基线"才算。

### 10.2.4 项目完成门禁（projectCompletionGate）

```ts
function projectCompletionGate(delivery) {
  return costApproved && 其余全部节点 completed;
}
```

节点 15 切"已完成"要求：**成本审批通过 + 其余全部节点 completed**。否则分析会把未完成项目当已交付（B5 修复）。节点 15 切换和"完成项目"按钮**共用**这个谓词（防两处口径漂移）。

## 10.3 财年归集：分析的数据地基

### 10.3.1 核心原则（F05 战场）

财年 = 7 月起算（FY2526 = 2025-07~2026-06）。归集规则：

| 数据 | 归属到哪个财年 | 依据 |
|---|---|---|
| 订单金额 | 交付完成所在财年 | 节点 15 实际完成日 |
| 销售金额（赢单） | 赢单所在财年 | `won_at` |
| 输单 | 输单所在财年 | `lost_at` |
| 活跃机会/项目 | **每个经历财年都统计**（可重复） | 生命周期窗口 |

⚠️ **绝不用 `updated_at`**——它是任何编辑都会变的，用它归集会失真。

### 10.3.2 财年窗口函数

```ts
// utils/fiscalYear.tsx
fiscalYearLabel(d)      // Date → 'FY2526'
parseFY('FY2526')       // → { startYear, endYear }
fyMonthWindows(fyRange) // → 12 个月的 [start, end) 窗口
```

月末窗口用**排他上界**：`[2025-07-01, 2025-08-01)`——否则 `<= 2025-07-31 23:59:59.999` 的写法容易丢最后一毫秒。

### 10.3.3 为什么"活跃期可重复统计、订单只归集一次"？

- **活跃**（进行中）：一个跨两年的大项目，在 FY2525 和 FY2526 都算"活跃"——管理层要看"当前有多少在途"；
- **订单/销售**：金额只能算一次，按完结事件（完成日/won_at）归到**唯一**财年——否则总额对不上账。

这个"重复 vs 单次"的区分是分析口径里最容易被搞错、被审计最多的地方。

## 10.4 成本对比（交付详情页）

DeliveryDetail 有成本对比 Tab：
- **概算**：取**匹配版本**（与交付 groups 版本一致）的报价参数算 `computeDeliveryEstGP3`；
- **实际**：从 `delivery_projects.actual_costs`（JSONB）+ `total_actual_cost` 读实际成本；
- **对比**：概算 vs 实际的各项差额（`buildCostLines` / `costBreakdown.ts`）。

⚠️ **版本匹配**是 #8 审计修复：此前成本对比虽按版本过滤 groups，财务参数却仍取"最新版本"，版本错配时数字失真。现在概算参数与 groups 同版本。

**成本覆盖留痕**：修改已审批交付的 `total_actual_cost`/`actual_costs` 会写审计日志（`afterUpdate` 钩子），**留痕但不强制重新审批**——因为实际成本本来就会随执行变化，重审会卡流程。

## 10.5 共享口径：analysisShared.ts

这是"三页同数"的保证。Dashboard / SalesAnalysis / DeliveryAnalysis 都展示月度订单、销售金额、财年趋势，**口径必须完全一致**。所以：

```
utils/analysisShared.ts
  ├── quoteProfitExTax / deliverySalesProfit    ← 月度订单/销售金额唯一定义处
  ├── projectMonthlySales                       ← 项目月度销售
  ├── fyMonthWindows                            ← 财年窗口
  ├── computeProjectOnTimeRate                  ← 节点按时率（无基线剔除）
  ├── projectCompletionGate                     ← 完成门禁
  └── getNodeDelay / getProjectDelay            ← 延期判定
```

页面只 import，不自己重算。**改口径只改一处**，且每个函数都有单测锁定。

## 10.6 销售分析的关键指标（口径速查）

| 指标 | 口径 |
|---|---|
| 新增机会金额 | 当月创建的机会金额（含税确认，单次扣税） |
| 赢单金额 | 当月 `won_at` 的机会金额 |
| 输单金额 | 当月 `lost_at` 的机会金额 |
| 加权管道 | 机会金额 × 赢率（蓝表 win_rate） |
| 赢率 | 蓝表 `calcBlueTableWinRate` 结果 |
| 月度订单 | 当月交付完成的订单金额（节点15完成日归集） |
| 概算/实际利润 | 交付的概算 vs 实际（未税口径） |

**金额口径提醒**：全应用金额按**未税**处理；只有概算汇总的少数几处是含税（B7 契约，见 07 章）。机会金额按含税确认、单次扣税（`deliveryExTax` 统一税率来源），避免重复计税。

## 10.7 本章小结

- 转交付 = 销售域的"赢单终极确认"；交付域有 15 个节点、两级审批（计划/成本）。
- 延期 = 实际/当前 vs **不可变的审批基线**；无基线不判定。
- 财年归集 = 业务完结事件时间（won_at/lost_at/节点15完成日），绝不用 updated_at；活跃可重复、订单单次。
- 跨页口径收敛在 `analysisShared.ts`，页面不重算。
