## 1.1 业务场景：从 Excel 宏到 Web 应用

在迁移成 Web 应用之前，这家公司（工业自动化/系统集成行业）的销售与项目报价是靠一个 **Excel `.xlsm` 宏表格**在维护的。宏表格能算成本、能算利润，但问题越来越突出：

- 多人同时编辑 → 版本错乱、相互覆盖；
- 公式写死在宏里 → 改一个口径要改几十处，还容易改漏；
- 没有权限概念 → 谁都能改价格；
- 报价 → 审批 → 交付，全靠口头/邮件流转，没有留痕。

于是有了这套系统。它的核心是把"销售业务的全生命周期"数字化：

```
客户线索
   │  录入销售机会（客户 / 金额 / 阶段 / 销售员 / 竞争情况）
   ▼
机会推进（信息→线索→机会→投标→议价→中标）
   │  每进入一个阶段记录时间戳（财年分析用）
   │  用「蓝表」做策略赢率分析（评估关键决策人支持度）
   ▼
报价编制（最核心的页面）
   │  按"项目版本 → 设备组 → 明细项"三级组织
   │  每行明细：物料成本 + 设计工时 + 装配工时 → 直接成本
   │  加价到售价 → 汇总出报价（含质保/风险/商业费用 → GP3 利润率）
   ▼
审批（报价 / 实施计划 / 成本对比 / 晋升转机会，四种审批流）
   │  提交后锁业务、审批人决策、通过则回写业务状态
   ▼
签单 → 转交付
   │  创建交付项目（15 个标准节点），成本对比（概算 vs 实际）
   ▼
项目执行 → 交付完成（节点 15）
   │  完成后财年归集：订单金额 / 销售金额 / 交付成本
   ▼
销售分析 / 交付分析 / 仪表盘（管理层看板）
```

**并行的一条业务线：工时管理**。员工每周填报工时，按成本中心归集（这个项目做了多少、销售跟单多少、质保多少、请假多少），部门经理/总监审批后，形成开工率、工时分布等统计，用于成本核算与人力评估。

> 💡 **一句话理解两套系统**：Budget 管"钱和单"（销售→报价→审批→交付），TR 管"人和时间"（任务→报工→审批→统计）。两者共用数据库——工时里用到的成本中心编号（`-S` 销售、`-E` 项目）就来自 Budget 的销售机会和交付项目表。


## 1.5 角色与权限的基本模型

这套系统的权限设计是整条学习路线的重点（06 章专门展开），这里先建立一个直观印象：

1. **权限是"字符串数组"**，存在 `users.permissions` 列。例如：
   ```
   ['仪表盘查看', '报价编制', '客户管理', '全部查看权限']
   ```
2. **每个功能声明自己需要什么权限**（满足其一即可），而不是"哪个角色能做什么"。
3. **`'全部查看权限'` 是万能权限**（相当于超管）。
4. **前端和后端各自维护一份权限清单**：前端用于隐藏入口/按钮（体验层），后端用于真正拦截（安全层）。**后端才是权威**。
5. **角色 `role` 仍在**，但职责收窄：`user/manager/director/admin`。主要用于工时系统的三级角色派生（见 11 章）和个别 UI 判断。

一个直观对比：

| 权限模型 | 传统 RBAC | 本项目 |
|---|---|---|
| 核心概念 | 角色 → 权限 | **权限数组直接挂用户** |
| 灵活度 | 加一个组合要新建角色 | 直接改用户权限数组 |
| 风险 | 角色爆炸 | 权限清单要前后端一致（有测试锁定） |

## 1.6 开发演进史（从 git 历史读项目成长）

理解这个应用怎么一步步长出来的，能帮你理解"为什么有些地方这么写"。

- **2026-06**：从 Excel 宏表格迁移成 React 前端原型，7 个 Phase 交付（报价编制 → 销售管理 → 审批 → 交付 → 客户 → 销售分析 → 系统管理）。
- **2026-07**：全栈化——引入后端 Express + PostgreSQL，认证系统（JWT + bcrypt），**全量审计修复**成为常态工作方式。
- **2026-08**：系统性地做"代码审计 + 测试 + 门禁"：
  - 三轮全量审计（后端/Budget/TR 分别审计修复）；
  - 引入 Vitest 单测并挂进 build 门禁；
  - 建立**家族缺陷清单**（12 个缺陷家族）；
  - 双应用业务规则审计（4 个 agent 并行 + 逐条复核）；
  - 决策点清单落地（补录窗口 = 当前周+前 4 周、补班日 = 工作日、日净工时 = 8h）；
  - 覆盖率从 5% 逐步提升到 19%+（纯函数层 80~100%）。

> 💡 从 git 历史能观察到本项目的**工作方法论**：每批功能都伴随"审计 → 修复 → 测试锁定 → 门禁 → 部署 → 验证"。这也是第 16 章练习要训练的思维方式。

## 1.7 本章小结

- 一套系统 = 两个前端（Budget 管钱、TR 管人）+ 一个共享后端 + 一个 PostgreSQL。
- 主流程是销售生命周期（机会→报价→审批→交付→分析），并行一条工时线。
- 权限是"权限字符串数组 + 前后端双守卫"，角色只是辅助。
- 这个应用的成长史 = 持续审计 + 测试 + 门禁的过程，这也是它质量好的原因。
