## 16.1 生产架构

```
腾讯云服务器 118.89.92.58（OpenCloudOS 9.6）
│
├── Nginx 1.26 (80)
│   ├── /                  → 导航页（index）
│   ├── /budget/           → Budget SPA（静态 dist）
│   ├── /timerecording/    → TR SPA
│   ├── /api/v1/*          → 反代 → Node :3001
│   └── /api/health        → 健康检查
│
├── Node.js 20 + Express（systemd 服务 budget-estimate-api，:3001）
│   ├── 源码在 /opt/budget-estimate-api（部署脚本直接发 src/，tsx 运行）
│   └── 运维脚本 /opt/scripts/（db-backup.sh / api-health.sh）
│
└── PostgreSQL 15（localhost:5432，库 budget_estimate）
    ├── 应用用户 budget_app
    └── 管理员 postgres
```

**关键点**：
- **后端以源码运行**（部署发 `src/`，服务用 tsx 跑）——部署不需要在服务器编译；
- **前端是纯静态**（vite build 产物），nginx 直接服务；
- **`/api` 全部反代到 Node**，浏览器同源（无 CORS 问题）。

## 16.2 部署脚本逐行解读

### 16.2.1 `deploy.sh`（Budget + 共享后端）

```bash
#!/bin/bash
set -e                        # 任何一步失败即停
cd "$(dirname "$0")"          # 切到仓库根

echo "=== 后端门禁（tsc + vitest）==="
cd backend
npm run build                 # ① 后端门禁：tsc + vitest，失败即停

echo "=== 构建前端 ==="
cd ../BudgetEstimateApp
npm run build                 # ② Budget 门禁：命名/lint/tsc -b/vite/vitest

echo "=== 部署前端 ==="
cd dist
tar czf - . | ssh tencent-budget "cd /usr/share/nginx/html/budget && rm -rf * && tar xzf -"
                              # ③ 前端产物打包 → ssh 到服务器 → 清空旧目录 → 解包

echo "=== 部署后端 ==="
cd ../../backend
tar czf - --exclude='*.bak' src/ | ssh tencent-budget "cd /opt/budget-estimate-api && tar xzf -"
ssh tencent-budget "systemctl restart budget-estimate-api.service"
                              # ④ 后端 src 推送 + 重启 systemd 服务
```

**流程**：门禁 → 构建 → 推送前端 → 推送后端 + 重启。`set -e` 保证任何一步失败都不继续（**门禁不过不部署**）。

### 16.2.2 `deploy-tr.sh`（TR 前端）

```bash
cd frontend
npm run build                 # TR 门禁：eslint + vite + vitest
cd dist
tar czf - . | ssh tencent-budget "cd /usr/share/nginx/html/timerecording && rm -rf * && tar xzf -"
```

**为什么 TR 只发前端？** 因为 TR 没有独立后端——它用**共享后端**（Budget 的 deploy.sh 已把后端发上去了）。

### 16.2.3 SSH 别名

`tencent-budget` 配置在 `~/.ssh/config`，用密钥 `~/.ssh/tencent_cloud` 免密登录。部署脚本靠这个别名 ssh 上去执行远程命令。

## 16.4 数据库迁移上服务器

迁移文件在 `backend/migrations/`，按编号顺序在服务器上执行：

```bash
# ① 先备份（服务器已有每日备份 cron，稳妥起见再手动一次）
ssh tencent-budget "/opt/scripts/db-backup.sh"

# ② 执行迁移（示例：045）
ssh tencent-budget "PGPASSWORD='Budget@Estimate2024!' psql -h 127.0.0.1 -U budget_app -d budget_estimate -f /opt/budget-estimate-api/migrations/045-tr-makeup-workday-normal.sql"
```

或本地把迁移文件传上去再执行：
```bash
scp backend/migrations/046-xxx.sql tencent-budget:/opt/budget-estimate-api/migrations/
```

**迁移纪律**：
- 按编号顺序执行，已应用的别重跑（多数幂等）；
- **改结构**的迁移要先备份；涉及生产数据的（UPDATE 回填）执行前确认影响行数；
- 生产实测迁移影响 0 行是常态（如 045 补班日回填），属预期（数据本就没脏）。

## 16.5 运维要点

### 16.5.1 健康检查

```bash
curl http://118.89.92.58/api/health
# → { "status": "ok", "database": "connected", "time": "...", "uptime": 12345 }
```

服务器上还配了 **cron 健康检查**（每 5 分钟 curl，失败写日志，仅服务停止才重启），以及 **每日 DB 备份**（`pg_dump -Fc` → `/opt/backups/db/`，保留 14 天）。

### 16.5.2 服务管理

```bash
ssh tencent-budget
systemctl status budget-estimate-api      # 状态
journalctl -u budget-estimate-api -f      # 实时日志
systemctl restart budget-estimate-api     # 重启
```

### 16.5.3 常见运维坑

| 坑 | 说明 |
|---|---|
| **时区** | 后端固定 `Asia/Shanghai`；若迁移到 UTC 机器，工时提交闸门/财年窗口会偏移 8 小时 |
| **uploads 目录** | 交付附件上传目录由服务启动自动重建，删了会随重启恢复（正常现象） |
| **备份优先级** | 迁移/清库前先备份；备份文件保留 14 天自动轮换 |
| **端口** | 后端 3001；nginx 只暴露 80；DB 5432 仅监听 localhost |
| **HTTP** | 生产当前纯 HTTP（118.89.92.58），`COOKIE_SECURE=0`；上 HTTPS 后设 1 并让 cookie 只走 HTTPS |

## 16.6 发布流程（完整版）

```
1. 本地：改代码 → 补单测 → npm run build（五关门禁）
2. 本地：git commit（信息写清"做了什么+为什么"）
3. 部署：./deploy.sh（Budget+后端）/ ./deploy-tr.sh（TR）
4. 验证：
   - curl /api/health → database connected
   - curl -I /budget/ 与 /timerecording/ → 200
   - 页面实际点一遍核心流程
5. 需要时：迁移（先备份）
6. 压测/审计后：把新教训写回家族清单
```

## 16.7 本章小结

- 生产 = Nginx（静态 + 反代）+ Node（源码运行，systemd）+ PostgreSQL。
- `deploy.sh`/`deploy-tr.sh` 封装了"门禁 → 构建 → 推送 → 重启"。
- 迁移手动按序执行，先备份；运维靠健康检查 + 每日备份 cron。
- 凭据只放本地/内部文档，外传需轮换。

**本章练习**：在本地走一遍 `deploy.sh` 的**门禁部分**（`cd backend && npm run build` + `cd ../BudgetEstimateApp && npm run build`），确认两条门禁链全绿——这是部署的第一步，也是你能安全做的部分。
