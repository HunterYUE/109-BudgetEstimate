## 5.2 20 个枚举（业务语义即字典）

`schema.sql` 顶部用 `DO $$ ... EXCEPTION WHEN duplicate_object` 幂等地创建枚举。它们直接映射前端 `types.ts` 的联合类型：

| 枚举 | 值 | 用在 |
|---|---|---|
| `sourcing_type` | PURCHASED（采购）/ SELF_MANUFACTURED（自制） | 物料、明细项 |
| `item_type` | COMPLETE_SET/COMPONENT/PART/SOFTWARE/SERVICE | 物料分类、明细类型 |
| `group_type` | EQUIPMENT/INTEGRATION/PACKAGING_TRANSPORT/PROJECT_DELIVERY/IMPLEMENTATION_EXPENSE/OTHER | **项目组类型**（决定料/工/费分解） |
| `review_status` | draft/pending/approved/rejected | 报价/版本/审批状态 |
| `account_type` / `credit_level` / `client_grade` | enterprise/subsidiary；A/B/C；A/B/C | 客户 |
| `decision_role` | 使用/技术/商务/高层 | 客户联系人 |
| `opportunity_stage` | 信息/线索/机会/投标/议价/中标 | 机会阶段（递进） |
| `opportunity_status` | 过程中/赢/输/冻结 | 机会状态 |
| `delivery_status` | 未开始/进行中/已完成 | 交付项目 |
| `node_status` | pending/in_progress/completed | 交付节点 |
| `approval_type` | quotation/plan/cost/promote | 审批类型 |
| `approval_action` | approved/rejected | 审批动作 |
| `veto_budget_option` | ok/possible/failed | 蓝表预算 |
| `timeline_option` | optimistic/neutral/negative | 蓝表时间线 |
| `influence_level` | high/medium/low | 蓝表角色影响力 |
| `role_type` | EB/UB/TB/COACH | 蓝表角色类型 |
| `pricing_level` | very_strong / strong / competitive / neutral / slightly_weak / weak / very_weak | 蓝表价格竞争力 |
| `reaction_mode` | G/T/EK/OC | 蓝表反应模式 |

> 💡 读法：先看枚举值，再想"这个值会出现在哪个业务动作里"。例如看到 `review_status` 四值，就知道"报价必须经过 草稿→待审→通过/驳回"这条路径，后端所有守卫都在保护这条路径。

## 5.3 核心表结构精读

### 5.3.1 group_items（报价最小单元，成本模型的落点）

```sql
CREATE TABLE group_items (
  id                 UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  group_id           UUID NOT NULL REFERENCES project_groups(id) ON DELETE CASCADE,
  item_no            INTEGER NOT NULL,
  item_type          item_type NOT NULL,
  component_id       UUID,                       -- 引用物料目录（SET NULL）
  code               VARCHAR(200) NOT NULL,      -- 物料编码
  description        TEXT NOT NULL DEFAULT '',
  qty_total          INTEGER NOT NULL DEFAULT 1,
  unit               VARCHAR(20) NOT NULL DEFAULT '个',
  sourcing_type      sourcing_type NOT NULL,
  unit_cost          NUMERIC(12,2) NOT NULL DEFAULT 0,     -- 单价（未税）
  design_hours       NUMERIC(10,2) NOT NULL DEFAULT 0,     -- 设计工时
  assembly_hours     NUMERIC(10,2) NOT NULL DEFAULT 0,     -- 装配工时
  design_hour_rate   NUMERIC(12,2) NOT NULL DEFAULT 0,     -- 设计工时费率
  assembly_hour_rate NUMERIC(12,2) NOT NULL DEFAULT 0,     -- 装配工时费率
  direct_cost        NUMERIC(12,2) NOT NULL DEFAULT 0,     -- 直接成本（计算列，页面计算后落库）
  margin_rate        NUMERIC(6,4) NOT NULL DEFAULT 0,      -- 毛利率 0.35=35%
  basic_price        NUMERIC(12,2) NOT NULL DEFAULT 0,     -- 预期售价
  accounting_price   NUMERIC(12,2) NOT NULL DEFAULT 0,     -- 取整售价（报价用）
  has_warranty       BOOLEAN NOT NULL DEFAULT false,       -- 是否计质保金
  note               TEXT NOT NULL DEFAULT ''
);
```

**一行的成本模型**（07 章公式化）：
```
物料成本   = unit_cost × qty_total
设计工时费 = design_hours × design_hour_rate
装配工时费 = assembly_hours × assembly_hour_rate × qty_total
direct_cost = 三者之和（取整到个位）
```

### 5.3.2 sales_opportunities（销售机会，状态机落点）

```sql
CREATE TABLE sales_opportunities (
  ...
  stage   opportunity_stage NOT NULL DEFAULT '信息',   -- 阶段：信息→线索→机会→投标→议价→中标
  status  opportunity_status NOT NULL DEFAULT '过程中', -- 状态：过程中/赢/输/冻结
  win_rate NUMERIC(5,2) NOT NULL DEFAULT 0,            -- 蓝表算出的赢率
  salesman / competitor / winner / reasons / notes ...
  promote_locked BOOLEAN NOT NULL DEFAULT false,       -- 转机会审批提交后锁定
  won_at  TIMESTAMPTZ,   -- 赢单时间（业务完结事件）
  lost_at TIMESTAMPTZ,   -- 输单时间
  lead_at/opportunity_at/bid_at/negotiation_at,        -- 进入各阶段的时间戳（COALESCE 首写）
  UNIQUE(sales_no)
);
```

⚠️ **财年归集的金科玉律**：`won_at`/`lost_at`/阶段时间戳是"业务完结事件"，**财年分析只用它们，绝不用 `updated_at`**（`updated_at` 是任何编辑都会变的，用它归集会把"这个月改过一笔旧单"算成"这个月赢的单"）。

### 5.3.3 delivery_nodes（交付节点）

```sql
CREATE TABLE delivery_nodes (
  delivery_project_id  UUID NOT NULL REFERENCES delivery_projects(id) ON DELETE CASCADE,
  node_no              INTEGER NOT NULL,            -- 1..15 标准节点
  name                 VARCHAR(500) NOT NULL,
  planned_start_date / planned_end_date   VARCHAR(100) NOT NULL DEFAULT '',  -- 计划时间（存字符串 YYYY-MM-DD）
  actual_start_date / actual_end_date / actual_date VARCHAR(100),
  baseline_planned_end_date VARCHAR(100) DEFAULT '', -- ★ 审批后不可变的延期基准
  status               node_status NOT NULL DEFAULT 'pending',
  comments             TEXT NOT NULL DEFAULT '',
  history              JSONB NOT NULL DEFAULT '[]',  -- 变更历史快照
);
```

⚠️ **基线不可变**：`baseline_planned_end_date` 在实施计划审批通过时写入（`planned_end_date` 的快照），之后改计划不影响它。这样"延期判定"用的是最初的审批基线，防止执行过程中人为把计划往后排从而"消除"延期。

### 5.3.4 JSONB 列：灵活结构放哪

| 表 | JSONB 列 | 内容形状 |
|---|---|---|
| `blue_tables` | `targets` | `[{"roleId":"...","targetSupport":3,"plan":"..."}]` |
| `delivery_nodes` | `history` | `[{"field":"status","oldValue":"...","newValue":"...","changedAt":"..."}]` |
| `delivery_projects` | `plan_approval` / `cost_approval` | `{"reviewer":"...","action":"approved","comment":"...","createdAt":"..."}` |
| `delivery_projects` | `actual_costs` | 按节点/组的实际成本结构 |
| `task_assignments` | `history` | 编辑历史快照 |

JSONB 的好处：结构灵活、可查询（GIN 索引）、一条记录一个对象。坏处：**没有模式约束**，容易塞进畸形数据——所以后端对写 JSONB 的接口都做了 `Array.isArray`/白名单校验（F01/C3/C4 修复）。

## 5.4 schema.sql 与 migrations 双轨制

这是本项目的**结构管理纪律**，写代码前必须懂：

| 概念 | 文件 | 作用 |
|---|---|---|
| **权威 schema** | `database/schema.sql` | 从零建库的唯一事实来源，**永远最新** |
| **增量迁移** | `backend/migrations/045-xxx.sql` | 应用到**已存在**的存量库的补丁 |

**三条纪律**：

1. **改结构的迁移（ALTER/CREATE TABLE/加列/加约束/加索引/加触发器）必须在同一 commit 同步更新 `schema.sql`**。否则：新库用 schema.sql 建出来缺这个结构，代码跑挂。
2. **纯数据迁移（UPDATE/INSERT 回填）不需要改 schema.sql**。
3. 每次改 schema 后建议验证：用 schema.sql 建临时空库执行应 0 错误，并与生产库做**六维结构签名对比**（表/列含类型默认值/约束/索引/触发器/枚举），逐项 diff 应 0 差异。

**为什么没有自动迁移 runner？** 迁移是手动按编号在服务器上 `psql` 执行的。多数迁移带幂等处理（`ADD COLUMN IF NOT EXISTS`、`DO $$ EXCEPTION WHEN duplicate_object`），已应用的重复跑也不报错。这种"半自动"方式对一个小团队是足够且可控的。

## 5.5 财年与统计口径（F05 的核心战场）

数据库侧的统计口径，见前端 `utils/analysisShared.ts` 与 `utils/fiscalYear.tsx`，几组必须统一的口径：

1. **财年**：7 月起算。`fiscalYearLabel(d)`：2025-07 → `FY2526`。财年窗口 `fyMonthWindows(fy)` 给出该财年的 12 个月。
2. **活跃期**：进行中的机会/项目，在每个财年都计入"活跃"（可重复统计）。
3. **订单/销售只归集一次**：以业务完结事件（节点15完成日 / won_at / lost_at）归属到**唯一**财年。
4. **月末边界**：用排他上界 `23:59:59.999`，否则 `date < nextMonthFirstDay` 会漏最后一天。
5. **时区**：全系统北京时间。后端 `index.ts` 顶部 `process.env.TZ='Asia/Shanghai'`；前端 `formatBeijing` 用本地拼接，不用 `toISOString()`（会转 UTC 差 8 小时）。

> 关于财年归属的完整规则，参见记忆 `analysis-fiscal-year-logic` 与 `delivery-analysis-kpi-rules`——这是本项目被审计最多、修过最多事故的领域之一。

## 5.6 本章小结

- 26 张表按业务域分层：销售（机会/蓝表）、报价（项目/版本/组/明细）、审批、交付、客户、用户/审计、工时。
- 枚举就是业务字典；状态字段一定有一条"状态机路径"。
- JSONB 提供灵活性，但要靠应用层白名单防畸形数据。
- `schema.sql`（权威）+ `migrations/`（增量）+ 六维签名对比 = 结构不漂移。
- 财年归集只信"业务完结事件时间"，不信 `updated_at`。
