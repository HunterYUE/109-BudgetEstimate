## 14.1 测试哲学：为什么"不 mock"

很多教程教你"用 mock 隔离依赖"，但本项目**刻意反着来**：

> **数据必须是真实数据库形状，直接作为参数传入；禁止 vi.mock 打桩业务/网络层。**

理由：
1. **mock 测的是你自己的假设**，不是真实行为。`parseDateKey('')` 的真实行为是返回 `1900-01-01`（不是报错、不是 Invalid Date）——只有真实数据直测才能发现并锁定这种真相；
2. **mock 会造假"一切正常"**：真实数据里藏着各种脏值（空串、越界、null、字符串数字），直测才能覆盖它们；
3. **纯函数不需要 mock**：把业务逻辑提成纯函数后，直接喂数据、断言结果，最干净。

唯一的例外场景（无法实例化的接线层）用**静态源码断言**（见 14.4）。

## 14.2 三种测试形态

### 14.2.1 形态一：纯函数直测（最常见，占比 95%）

```ts
// tests/calculations.test.ts
import { calcDirectCost } from '../src/utils/calculations';

describe('calcDirectCost 直接成本', () => {
  it('qtyTotal=0 合法值不得被吞成 1', () => {
    expect(calcDirectCost({ unitCost: 100, qtyTotal: 0 })).toBe(0);
  });
});
```

**写法要点**：
- 测试放根级 `tests/`（不在 src/，规避 lint-naming 对 snake_case 的扫描）；
- 直接构造"真实数据库形状"的对象传入；
- 涉 `now` 的函数用 **asOf 注入**：

```ts
// backfillWindowStart 接受 now 参数 → 测试传固定时刻
expect(backfillWindowStart(new Date('2026-08-17'))).toBe('2026-07-20');
```

### 14.2.2 形态二：静态接线断言（锁"配置收敛"类回归）

有些接线层**无法实例化**（依赖 DB/中间件链），比如 `routes/index.ts` 的守卫挂载。怎么测？直接读源码断言结构：

```ts
// tests/route-guards.test.ts
import { readFileSync } from 'node:fs';

it('路由守卫必须引用 permissions 常量，禁止内联权限数组', () => {
  const src = readFileSync(new URL('../src/routes/index.ts', import.meta.url), 'utf-8');
  expect(src).not.toMatch(/requirePermission\s*\(\s*\[/);   // 不允许内联数组
  expect(src).toMatch(/WRITE_GUARD/);                        // 必须引用配置常量
});
```

这**不是 mock**，而是"锁配置收敛"——防止未来有人图省事在挂载处写死权限数组，导致 `permissions.ts` 变成摆设。它和纯函数测试互补。

### 14.2.3 形态三：性能基准（不进门禁、无断言）

```ts
// tests/bench/*.bench.ts —— 由 vitest.bench.config.ts 收集
import { bench, describe } from 'vitest';

describe('buildTypeHours 全量聚合', () => {
  bench('100,000 条工时记录', () => buildTypeHours(bigRecords), { time: 1000 });
});
```

- 运行方式 `npm run bench`；
- **测量工具，无断言，不进 build 门禁**（`*.bench.*` 命名天然不被默认 include 匹配）；
- 目的：给热路径立一个"可复现耗时基线"，大型重构触碰时人工对比（详见 `docs/性能基准基线.md`）。

## 14.3 测试分布与覆盖目标

| 代码库 | 数量 | 重点覆盖 |
|---|---|---|
| backend | 196+ | 工时计算 / 机会状态机 / 审批映射 / 权限配置 / 错误码 / 静态接线 |
| Budget | 195 | calculations / blueTable / analysisShared / costBreakdown / api 契约 |
| TR | 126 | timeStats / backfillWindow / withdrawWindow / timeSlots / costCenter |

覆盖率 `npm run coverage`（v8 provider，`include: ['src/**']`）：
- 纯函数层 80~100%；
- 页面/route 层被稀释（几十分之一）→ 整体 7~19%。

**为什么页面层覆盖率低是"正常的"**：页面是"胶水代码"（拉数据 + 渲染），用 jsdom 才能测，收益低、维护贵。项目的策略是**把逻辑都下沉到纯函数**，页面尽量薄，所以测纯函数就是测业务。

## 14.4 门禁链（build 脚本串起五关）

**Budget** 的 `npm run build`：

```
node scripts/lint-naming.cjs   # ① 命名规范
npm run lint:quiet             # ② ESLint（--quiet 只留 error）
tsc -b                         # ③ 类型检查（必须 -b，见 02 章陷阱）
vite build                     # ④ 生产构建
npx vitest run                 # ⑤ 全量单测
```

**backend**：`tsc && vitest run`
**TR**：`eslint . --quiet && vite build && npx vitest run`

**门禁的意义**：测试失败 = 构建失败 = 部署失败。任何改动在进生产前必须过完全套检查。部署脚本（16 章）会先跑门禁再发。

### 14.4.1 lint-naming 到底查什么

`scripts/lint-naming.cjs` 扫描前端 `src/` 下所有 `.ts/.tsx`，查两件事：

1. **蛇形键名**（`\b[a-z]+_[a-z]+\w*\b`）：前端内部应用 camelCase。白名单（`API_BODY_FIELDS`）放行确实要发给后端的字段（`client_name`、`qty_total`...），`FALSE_POSITIVES` 放行枚举值（`in_progress`...）。
2. **裸 `fetch()`**：绕过 api.ts 直接请求，会漏掉缓存/转换/401 处理。

### 14.4.2 `tsc -b` 的陷阱（再强调）

这个项目的 `tsconfig.json` 只有 `references`（project references）。裸 `tsc --noEmit` 对空文件列表**静默通过**，等于没查类型。**必须用 `tsc -b`**（build 模式，按引用图逐个编译）。这是记忆 `tsc-solution-config-trap` 记录的教训。

## 14.6 一个完整的测试驱动例子（TDD 流程）

以"新增一个 `isWorkday` 纯函数"为例（2026-08-14 审计日流程）：

1. **写测试**（先红）：
   ```ts
   it('补班日（周六）→ 工作日', () => expect(isWorkday('2026-02-14')).toBe(true));   // 2026 补班日
   it('普通周六 → 非工作日', () => expect(isWorkday('2026-02-21')).toBe(false));
   ```
2. **写实现**（变绿）：
   ```ts
   export function isWorkday(dateKey) {
     const d = parseDateKey(dateKey);
     const wd = d.getDay();
     return (wd >= 1 && wd <= 5) || isMakeupWorkday(dateKey);
   }
   ```
3. **跑门禁**：`npm run build` 五关全过。
4. **补防**：在家族清单对应条目确认防线。

## 14.7 本章小结

- 测试哲学：真实数据形状、无 mock、asOf 注入、静态接线断言。
- 三种形态：纯函数直测 / 静态源码断言 / 性能基准。
- 门禁链五关：命名 → lint → tsc -b → build → vitest。
- F01~F12 是沉淀的踩坑清单，提交前 30 秒自查。

**本章练习**：给一个现有纯函数（如 `utils/timeFormat.ts` 里的函数）补充 3 条边界测试（空值/越界/脏数据），跑 `npm test` 并确认通过。然后读 `docs/家族缺陷清单.md` 的 F01 和 F04，用清单检查你刚写的测试是否覆盖了对应边界。
